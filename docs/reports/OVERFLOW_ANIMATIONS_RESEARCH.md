# OverflowAnimations research and implementation plan for Aurora

Reviewed 2026-11-18 against Polyfrost's modern Fabric source, version 5.1.11 at `65f33101479f90b28af190bad1fe003bf0f52574`, and Aurora master at `f6affe83`. The current Polyfrost project is an Animatium fork in `OverflowAnimationsV2` on `stonecutter`. The similarly named `Polyfrost/OverflowAnimations` is the archived predecessor. The review covered the first-person renderer, equip tracking, entity swing state, fishing, movement and the server feature boundary. Aurora's version-specific targets below were checked against its existing mixins, Loom sources for 26.2 and 26.3, and 26.1.2 client bytecode. [Pinned OverflowAnimations source][overflow] · [Archived predecessor][archived] · [Current project listing][modrinth]

## Recommended scope

Start with **Reduced Hand Sway** and one **Compact Eat/Drink** preset. Both have a visible effect in ordinary play and can live in the local hand renderer. Follow with **No Use Equip Dip** and an optional **Slot-Only Re-equip** mode after verifying how each version selects its visible stack. Evaluate legacy fishing rod pose, sword-block pose and local third-person movement separately because they cross additional render paths.

Aurora already eases the first-person swing argument, scales camera bob and offers directional damage tilt, idle held-item sway and hotbar bounce. Its per-item adjustments and shield styles share the first-person item submission hook with idle sway and the persisted legacy swing arc. The owner removed the Swing Style selector on 2026-10-30, and saved values still apply. The catalog advertises retro backwards walking and sneak poses, but the reviewed tree has no corresponding Animations settings or hooks. Factory defaults already turn the Animations master switch on with a linear swing curve, so each new visual needs a vanilla or off default. ## What OverflowAnimations does and how to implement it independently

### 1. Hand sway and eat/drink

**In OverflowAnimations.** View-driven hand sway comes from the difference between current view angles and the hand renderer's smoothed bob angles. Overflow can zero the coefficient applied to that difference in the two-hand entry point. Eating and drinking are taken from the existing consumption transform. Overflow adjusts its translation, centering, rotations and intensity. Its “consume speed” changes the exponent that shapes the animation's approach to the face, while actual use duration comes from the game. These hooks sit separately from the late item-model transform, where its general position and scale adjustments run. [26.3 hand hooks][oa-hand-motion] · [Pre-26.3 hand hooks][oa-old-hand-motion]

The position hooks illustrate why the stage matters. A model-only adjustment runs immediately before item submission. The option that scales the whole movement instead compares the customized resting pose with the inverse of the uncustomized resting pose and applies that difference before the motion. Its automatic legacy position mode also checks whether a resource pack overrides that display context. Keep Aurora's existing model transforms for the first pass and verify that the use animation looks right with those transforms enabled. [Early and late transform stages][oa-position-stages] · [Automatic position selection][oa-item-util] · [Resource-pack transform detection][oa-pack]

**In Aurora.** For Reduced Hand Sway, scale the existing view-angle lag rotations in the hand renderer. Keep world camera bob, the player's View Bobbing option and Aurora's Idle Sway independent. For Compact Eat/Drink, use the native consume branch and reduce lateral travel and vertical bob with Aurora-tuned values. Use the current hand's existing use progress and let the game choose item models, duration, completion and particles. Match a visual goal from footage, such as keeping the crosshair clear while still visibly bringing food or a potion toward the face. The setting applies to the active eating or drinking hand. Check left-handed main and offhand use, other use animations, maps and bare arms. Verify that the new transform composes predictably with existing item scale and idle sway. Give the consume preset priority over idle sway for that hand only if the two motions conflict in capture.

### 2. Equip dip and slot-only re-equip

**In OverflowAnimations.** A held item can dip and rise because the displayed stack changes, because a use action resets the hand height, or because the main-hand target height follows the attack-related swap scale. Overflow handles these through distinct hooks. Its legacy equip modes change the height and stack-replacement decisions, track a copy of the visible stack and, for 1.7, track the selected slot. On 26.3 it transfers the extra main-hand stack through the extracted render state. A second hook set observes the use path, including a creative block-use exception. The published option for disabling equip animation and the legacy swing option also act at different points. [26.3 equip state][oa-equip] · [Earlier equip state][oa-old-equip] · [Use-triggered equip and swing][oa-use] · [26.3 render-state handoff][oa-equip-submit]

**In Aurora.** Implement No Use Equip Dip narrowly. Confirm the version's use animation notification, then suppress the visual hand-height reset for successful uses covered by the option. Preserve inventory mutation, the interaction result, normal swap behavior and genuine use poses. If a version shares the notification with another caller, restrict it at the rendering-state boundary or the specific visual call site. Test item use that decrements a count, use of the last item, replacement with a different item, a failed use, placement in creative and the offhand.

Treat Slot-Only Re-equip as a second change. For the main hand, a selected-slot change triggers a dip, including a move between two slots holding the same type. Same-slot count or durability changes update the visible item immediately. Preserve vanilla animation when the item type changes in place, and preserve model and component updates that affect appearance. Offhand and hands-busy behavior can stay on their vanilla path. If a model requests no swap animation, respect it and document that exception. Prefer the vanilla visible-stack lifecycle and adjust the trigger decision at the hand-state owner. A delayed visual swap must keep the displayed stack, model, use metadata and hand height coherent, especially in 26.3 where model state is resolved before submission. Store only the rendering information needed to compare transitions and clear it on player/world change or when the option turns off. Repeated scroll, swap-hands and profile changes during a dip should settle on the latest actual inventory state.

### 3. Swing shaping and blocking poses

**In OverflowAnimations.** Custom swing duration wraps a `LivingEntity` duration calculation. Older versions use a single swing counter. In 26.3 each swing has a description carrying its hand, animation and duration, and Overflow can change the running description on an item swap. Its local-looking mining and missed-hit features can start the entity swing state directly, while some use/interact paths bypass local animation and send the swing packet themselves. Actual non-shield blocking is a separate render branch. Overflow uses that branch to replace the first-person block pose and applies a rendered swing transform during selected use poses. [Swing duration and item swaps][oa-swing] · [Local swing and packet helpers][oa-swing-util] · [Block pose hook][oa-block] · [Swing during use][oa-use-pose]

**In Aurora.** Reuse `AnimationCurves.applySwing` for any additional swing shaping. If players ask for faster-looking motion, retime the render phase of an existing swing while preserving its endpoints and monotonicity. Keep hand selection, duration and restart eligibility in vanilla's swing state. Check both the standard swing and 26.3's distinct thrust path. A real duration change changes when vanilla can start another swing, which is outside this report's cosmetic scope.

A later **Classic Block Pose** can be a local first-person visual for an item already in vanilla's blocking-use state. Derive it from authentic legacy footage, take the arm and use state from the renderer, and apply a single mirrored pose inside that hand's pose stack. The shield retains its existing Aurora style and ordinary swords retain their actual use behavior. If there is demand for a sword-and-shield block-hit look, specify it separately around a real offhand shield block and test the two visible hands together. Keep the shield visible and its blocking feedback truthful. No Use Equip Dip must leave a real shield raise and its pose intact.

### 4. Fishing rod and third-person movement

**In OverflowAnimations.** Fishing rod behavior spans the held transform, cast-model selection and the endpoint of the rendered fishing line. The line renderer computes a camera-relative endpoint for the local first-person view and a body-relative endpoint in third person. Overflow alters those calculations alongside its rod pose. Its 1.7-style third-person cast can substitute a stick model, independently of the line. [Rod pose and item submission][oa-rod-pose] · [Fishing line source][oa-fishing] · [Cast model selection][oa-fishing-model]

**In Aurora.** Keep an initial rod preset local and first-person. Fit the rod pose and the rendered line origin in the same change, using the same reference points and correct holding arm. Verify cast and reel, both hands, wide/narrow FOV, swing in flight and viewpoint changes. A rod pose that separates the line from the rod tip fails acceptance. Start with the existing model and line pipeline so resource packs and both graphics backends retain their normal rendering paths.

**In OverflowAnimations.** Sneak behavior is split between camera eye-height interpolation, humanoid render-state and pose hooks, and a separate server-enabled collision/dimensions change. Its backwards-walk option hooks live body rotation in `LivingEntity`. Its legacy damage-tilt option zeros the hurt direction used by `bobHurt`, while Aurora's existing option intentionally rolls with the hit direction. [Sneak camera][oa-sneak-camera] · [Sneak render-state extraction][oa-sneak-state] · [Backwards walking][oa-walk] · [Damage tilt][oa-bob] · [Server-enabled sneak dimensions][oa-sneak-dimensions]

**In Aurora.** A later retro movement pass can adjust the local avatar's model pose in third person using the vanilla stance and render inputs. For backwards walking, derive a display-only body angle from the avatar's travel direction and maintain continuity through zero speed and angle wraparound. For crouching, keep feet grounded and equipment aligned with the posed model. Match cape, armor and held items to the same display pose. Keep the vanilla camera point of view, collision, name visibility, movement and networked angles. Start with the local avatar, which keeps other players' visual tells consistent and avoids imposing per-entity work on crowded scenes.

| 26.2 | `ItemInHandRenderer.submitHandsWithItems` → `submitArmWithItem`. The consume transform still receives the stack and player. Existing Aurora item adjustments run before `renderItem`. | `ItemInHandRenderer.tick()` and `itemUsed(hand)`. |
| 26.3 | `FirstPersonHandsAndItemsRenderer.submitHandsWithItems` → `submitArmWithItem`. The consume transform reads extracted use time and duration. Existing Aurora item adjustments run before `ItemStackRenderState.submit`. | `FirstPersonHandsAndItems.tick(LocalPlayer)` owns height and stack state. `LocalPlayer.itemUsed` forwards the visual reset and `FirstPersonHandsAndItems.extractRenderState` feeds submission. |

Work in the versioned adapters at the narrowest native render or hand-state hooks. Use the existing late Aurora hook for additive item offsets and the earlier, action-specific hooks for view lag or use motion. Avoid a second renderer and duplicate pose application when the vanilla call is reachable from multiple branches. At a shared submission boundary, check hand, active use animation and display context; restrict special-case paths such as maps and spears explicitly. Apply transforms within the hand-local pose stack and avoid per-frame stack copies, registry lookups and scratch allocations. Move any new primitive-only curve or transition policy that the adapters actually share to core. [26.1.2 adapter][aurora-hand-261] · [26.2 adapter][aurora-hand-262] · [26.3 adapter][aurora-hand] · [Adapter architecture][aurora-arch] · [Parity ADR][aurora-parity]

Use Aurora's Animations settings and existing settings widgets. Read the master switch and the new option when the hook runs. Add neutral defaults to both the Java schema and the release defaults resource. Include the fields in the feature reset prefixes and exercise profile import with an older profile missing the fields. Use a migrator only if a future change alters an existing saved preference or its meaning. Register each required mixin and its owning config gates in the versioned mixin lists and `FeatureCatalog`. For confirmed overlap with `overflowanimations`, stand down only the conflicting mixin when possible, so unrelated animation options remain available. Verify that partial application falls back safely and that diagnostics distinguish stand-down from failure. Update the Animations description and regenerate fair-play documentation when a feature lands. [Contributor guide][aurora-guide] · [Mixin ADR][aurora-mixins] · [Fair-play ADR][aurora-fair]

## Source and gameplay boundaries

The reviewed Overflow files carry GPL-3.0-or-later headers. Its root license adds an exception for combining the mod with Minecraft and LGPL components under the terms specified there. Aurora's license is MIT. Use the observations in this report as functional requirements. Derive Aurora's selectors and state ownership from its own tree and the target Minecraft versions. Tune original poses from recordings or a stock legacy client and record the footage and tuning decisions in the implementation PR. Keep Overflow's source, tables of transforms, assets and config presets out of the implementation. [Overflow license and exception][oa-license] · [Example source header][oa-header] · [Aurora license][aurora-license]

Keep changes in local rendering or the client-side state used only to draw the hand. Overflow also offers server feature negotiation, miss-delay changes, use while mining and altered crouch dimensions. Its visual and gameplay options share names in places, so use the hook and state being changed to decide if an effect fits. Aurora's cosmetic work should preserve attacks, item-use decisions, cooldown logic, mining, hitboxes, movement, packet contents and packet timing. Exclude synthetic hit or crit feedback from the proposed settings. [Overflow networking][oa-network] · [Miss behavior][oa-miss] · [Mining/item interaction][oa-mine] · [Sneak dimensions][oa-sneak-dimensions] · [Aurora fair-play rules][aurora-fair]

## Implementation acceptance

- Run `python tools/parity.py` and boot each supported line through a disposable Loom game dir. Check mixin health on each line. Deliberately disable the new mixin in a separate boot and verify that the client starts and reports the disabled capability. Use the renderer matrix for OpenGL and the supported Vulkan path before release. [Minecraft versions and backends][aurora-versions] · [Mod matrix][aurora-matrix]
- Capture identical actions with factory defaults, the master switch off, and each new setting on. Fixed camera/FOV captures should cover right- and left-handed views, both usable hands, the feature's active action and return to idle. Include item scale, shield styles, idle sway, hotbar bounce and a pack with custom hand transforms. Boot a compatible Overflow installation alongside Aurora to check any observed hook conflict.
- For equip logic, use a short deterministic sequence of same-slot count/damage updates, same-item slot switches, different-item switches, empty hands, rapid swaps and an old profile import. Check that the shown model tracks the correct stack, with no invisible or stale item after an interrupted dip. Compare actions with the settings on and off in a controlled server session if a proposed hook is near item use or attack. A renderer-only feature should produce the same gameplay decisions and outgoing traffic for the same inputs.
- Compare disabled and enabled frame cost, including two visible hands and crowded third-person scenes if model poses are added. Use Aurora's existing diagnostics and release overhead check. [Overhead budget][aurora-budget]

This report is a source review. The proposed animations still need runtime tuning and the acceptance runs above.
