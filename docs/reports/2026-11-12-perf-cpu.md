# Step 8, PR 2: per-frame CPU work (2026-11-12)

Branch `feat/perf-cpu`, stacked on `feat/perf-foundation` ([ADR 0009](../adr/0009-client-optimizations-aurora-owns.md)).

## What changed

| Optimization | Gate | UI | Mixins (all shared) |
|---|---|---|---|
| Sound Listener Throttle | `perfSoundListenerThrottle` | config only | `SoundEngineListenerMixin` |
| Debug Entry Cache | `perfDebugEntryCache` | Settings → Performance → Debug Screen | `DebugScreenEntryCacheMixin` |
| Merge Text Decorations | `perfMergeTextDecorations` | config only | `FontDecorationMergeMixin` |
| GUI Item Baking | `perfGuiItemBaking` | config only | `TextureManagerAnimationMixin`, `ItemStackRenderStateAnimationMixin`, `CuboidItemModelAnimationMixin`, `GuiItemAtlasBakingMixin` |

- **Sound listener.** A listener update equal to the last one sent is not queued for the sound thread. The memory is cleared when the sound library restarts.
- **F3 entries.** Each entry's output is recorded and replayed for 50 ms (one game tick). The cache is dropped on a level change.
- **Text decorations.** Underline and strikethrough segments that continue exactly (same height, colours, shadow and depth, starting where the last ended) become one quad. The run is emitted before `bounds()` or `visit()` reads the text. `discardEffects` (26.2 and later, used by outline text) drops pending runs; that hook is optional because 26.1 lacks the method.
- **GUI items.** Vanilla throws away the atlas slot of every animated item after each frame. An item animated only by its sprites now keeps its slot and is redrawn when `TextureManager.tick()` has advanced the sprites since it was drawn. Items with a glint or a special animated model keep vanilla's behaviour.

## Evidence

26.3 OpenGL, 856×519 window, unlocked frame rate, factory settings. "B" is the same boot with the named mixins disabled through `-Daurora.mixin.disable`.

| Scenario | Aurora | B | Measure |
|---|---|---|---|
| Survival inventory, 36 sprite-animated items | 714–777 fps | 601–690 fps | probe FPS, 8 s (about +12%) |
| Same | 2.7% | 4.8% | render-thread JFR samples in `GuiRenderer.prepareItemElements` |
| F3 open | 7.5% | 9.2% | render-thread JFR samples in `DebugScreenOverlay.extractRenderState` |
| Standing still | 0 | 395–434 | sound listener updates applied per second (probe mixin counter) |
| Settings page with Aurora's Underline text option | about 30 | about 200 | text decoration quads per frame (probe counter, 6.7× fewer) |

Line and backend coverage:

- Boots on 26.3 OpenGL and Vulkan, 26.2 OpenGL and Vulkan, and 26.1.2 OpenGL applied every mixin (91, 90 and 91) and logged no Aurora warning or error.
- On every line, the listener counter reads 0/s while still and underlined text stays merged.
- A first 26.1.2 boot showed that `discardEffects` does not exist there. Fail-soft turned the merge off for that session; the hook is now optional, and a rerun applied it.
- Two inventory screenshots 1.5 s apart show the same 27 of 36 slots changing with and without baking, so cached items keep animating.
- Underlined UI looks the same merged as per character.
- Vulkan inventories and F3 render correctly.

## Compatibility: ImmediatelyFast

A 26.3 boot with matrix set A froze animated inventory items: 0 of 36 slots changed between two screenshots. Isolation runs:

- Sodium alone: 24 of 36 slots changed.
- Set A with GUI Item Baking disabled: 27 of 36.
- Set A with baking on: 0 of 36.

ImmediatelyFast 1.17.1's `batch_animated_item_updates` sends animated items to its own `GuiItemAtlas` subclass, and keeping their slots there breaks its per-frame batch. That feature owns the same cost, so the four baking mixins now yield to `immediatelyfast` through ADR 0009's stand-down.

The rerun logged "All 93 Aurora mixins applied or stood down (4 stood down)", with each mixin "handled by immediatelyfast", and 24 of 36 slots animated. `DiagnosticsTextTest` covers the report's stand-down section.

## Measured and dropped

A stress scene on 26.3 (2048 closed chests in view, 200 resting pigs) was recorded with JFR, with FPS around 190:

- `LevelChunk$BoundTickingBlockEntity.tick` took 0.4% of render-thread samples. That is the per-chest ticker wrapper that **Idle Block Entity Ticks** would skip; `ChestBlockEntity.lidAnimateTick` itself took 0 samples.
- `SynchedEntityData.get` took 0.1%. That is what **Synced Data Copies** would replace with plain fields.

Neither clears the noise in a scene far denser than normal play. Both would also add risk: four mixins for lid state, and copies that must track every packet-driven data change. Under ADR 0009 neither is shipped.

The spawner half of Idle Block Entity Ticks was dropped before measuring: with no player near, vanilla's client tick is only the `isNearPlayer` check, and skipping it safely needs the same check.
